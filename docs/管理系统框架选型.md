# 管理系统框架选型

## 结论

管理后台采用成熟的 **RuoYi-Vue-Plus 6.x** 作为基础框架，再按本项目业务进行模块扩展。当前仓库中已有的 FastAPI 和 Vue 最小代码保留为原型与接口验证用途，不作为正式管理系统底座。

## 选择理由

- 后端采用上游当前版本的 Spring Boot 4.1、MyBatis-Plus 和 Sa-Token，前端采用 Vue 3、TypeScript、Element Plus、Vite 和 ECharts。
- 已经提供用户、角色、菜单、部门、字典、日志、文件和代码生成等后台通用能力。
- 适合管理系统的权限、审计和组织结构需求，减少重复开发。
- 前端可以在现有布局中增加地图、轨迹、设备和风险事件页面。

## 系统边界

```text
RuoYi-Vue-Plus 管理平台
  ├─ 用户/角色/权限
  ├─ 骑手与设备管理
  ├─ 实时地图与轨迹
  ├─ 风险事件与处置
  └─ AI 报告

设备端 ── MQTT ──┐
                 ├─ 数据接入适配层 ── 管理平台数据库/API
AI 服务 ─ REST ──┘
```

## 业务扩展模块

建议在框架业务模块下增加：

- `rider`：骑手信息和设备绑定
- `device`：设备状态、电量、GPS、摄像头和固件信息
- `track`：定位点、速度和轨迹查询
- `risk-event`：风险等级、事件图片、位置、处置状态
- `ai-report`：模型版本、风险原因、建议和置信度
- `realtime`：MQTT 消息消费和 WebSocket 推送

## 服务拆分

- **管理平台**：Java/Spring Boot，负责权限、业务数据、查询和后台页面接口。
- **设备接入适配层**：优先作为管理平台模块，后续设备规模增大时再独立服务。
- **AI 服务**：Python，负责 YOLO、道路分割、多传感器融合和 VLM 调用。
- **设备端**：Python/C++，负责采集、本地判断、报警和上报。

## 迁移原则

1. 不继续扩展自制的后台 CRUD、权限和菜单系统。
2. 先固定 RuoYi-Vue-Plus 上游版本，再在业务模块中适配本项目。
3. 当前 FastAPI `/health` 和演示接口只用于原型验证；正式接口迁移到管理平台后再下线。
4. AI 服务保持独立，避免把模型依赖直接塞进 Java 管理后台。
