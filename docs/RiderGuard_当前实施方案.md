# RiderGuard 当前实施方案

> 状态：现行方案。项目的开发、接线和验收以本文为基线；旧的树莓派／RK3588 板端 AI 方案和“STM32 运行 YOLO”方案已取消。本文中的演示阈值与模拟信号不得当作道路安全标准或真实交通信号。

## 1. 要解决的问题

外卖骑手在配送中可能经过人群密集区域并超速。系统要在设备端及时提醒骑手，同时把定位、车速、现场照片和事件处理过程留在后台，供管理人员实时查看与事后复盘。首版先完成“人群密集识别—限速切换—超速提醒—风险事件—地图处置”闭环。

## 2. 唯一现行架构

```text
OV2640 前向摄像头 ─┐
GNSS 定位 ─────────┤
霍尔车速 ──────────┼─ STM32F407 ─ 4G/HTTPS ─ 若依设备接口 ─ 数据库/私有照片
IMU（后续阶段） ────┘       │                         │
                         └─ 本地蜂鸣器/状态灯          ├─ 独立 Python YOLO 服务
                                                    └─ 管理后台/高德地图/事件处置
```

- **STM32**：采集、缓存、上报、按最后一份有效策略本地比较车速并驱动提醒；不运行 YOLO、道路分割或视觉大模型。
- **Python 推理服务**：接收 JPEG，在前方有效区域内检测行人并返回人数。模型权重、阈值和区域须用实际车载照片验证；服务可与若依分机部署。
- **若依平台**：设备凭证和骑手绑定、限速策略、轨迹、风险事件、照片权限、处置审计及地图。网页关闭后，设备提醒和后端事件记录仍正常工作。

## 3. 首版数据与判定流程

1. 骑行时约每 1 秒上报一次设备 ID、唯一采样编号、采集时间、原始 GNSS 经纬度、定位有效状态、速度，以及可用时的航向和定位精度。无效定位仍记录采样，但不在地图上绘点。
2. 骑行中约每 3～5 秒上传一张压缩 JPEG，不传实时视频。这个频率是联调起点；须实测 4G 流量、功耗、图像大小、识别延迟，再决定是否改为动态采样或事件触发。图片与同一设备和采集时间关联；断网时排队并按原采样编号补传。
3. 云端 YOLO 只统计前方有效区域内的 `person`。连续两张达到可配置人数条件进入“人群密集”状态；连续三张低于条件退出。识别失败显示失败状态，不按“无人群”处理。
4. 若依返回当前 `NORMAL`／`CROWD` 限速档位及有效期。演示值为普通路段 25 km/h、人群密集区域 10 km/h；正式阈值须实车测试和业务确认。
5. STM32 每次取得车速都在本地比较有效限速，超速立即鸣叫和亮灯。后端同步生成超速事件，记录速度、当时阈值、位置、关联照片和时间；管理员可在地图与轨迹中复盘并留下处置记录。

设备协议和接口细节见 [RiderGuard_设备云端联调.md](RiderGuard_设备云端联调.md)。GNSS 原始坐标保存在服务端，展示时转换到高德底图坐标；地图为近实时轮询，不把插值动画当作真实采样。

## 4. 阶段边界

| 阶段 | 交付重点 | 验收依据 |
| --- | --- | --- |
| A：模拟链路 | 模拟设备与模拟人数、两档限速、超速事件、照片权限、地图轨迹、断线补传 | 从模拟上报到设备提醒和后台处置全链路可复现 |
| B：真实设备 | ST-LINK 调试、GNSS/霍尔/OV2640/4G 实际接入、蜂鸣器与状态灯、稳定供电和离线存储 | 实际照片与定位进入系统，断网恢复后不重复生成事件 |
| C：真实视觉 | 云端 YOLO 权重、相机视角和前方区域校准，评估误检、漏检和延迟 | 用实拍验证集而非模拟人数完成密集场景测试 |
| D：扩展风险 | 道路分割/道路类型、IMU 急刹与摔倒、多传感器融合、事后 VLM 解释 | 各自建立数据集、指标和误报处理流程后逐项接入 |

“道路检测”是后续独立任务：先明确要识别道路区域、路口还是道路类型，再收集车载相机实拍图、标注和对应定位，训练或微调适合的分割/分类模型。预训练 YOLO 行人检测不能直接代替道路语义识别。视觉大模型只用于非实时事件解释，不参与首版即时限速。

当前红绿灯 `DEMO-001` 仅用于界面与协议联调；没有真实信号数据源，不向骑手提供真实路口通行指令。真实信号联动需另行解决合规数据源、路口/行进方向匹配、时间有效性和失效降级。

## 5. 实施约束与当前状态

- 管理后台、设备 HTTP 接口、模拟器和 Python 推理服务已有代码；本地启动默认 `mock`，不代表云端 YOLO 已完成部署或模型效果已验证。
- 目前只有板端限速提醒 C 适配模块，尚无针对已到货 STM32 板卡的完整外设固件。摄像头 DCMI 引脚、4G 的确切 SKU 与供电、蜂鸣器/LED GPIO、保护电路和离线存储须按实物核实。
- 设备请求使用 HTTPS 和设备凭证；照片保存在私有目录，仅授权后台用户查看。Python 服务与若依之间使用内部密钥及受保护连接，不把推理端口直接暴露为公开图片接口。
- 任何模型权重、采集数据、设备凭证和私钥均不提交到 Git。正式部署须先备份数据库，并核验迁移和服务健康；健康接口可用不等于实拍推理有效。

## 6. 取消的旧要求

- 不采用 Raspberry Pi 5、RK3588 或 STM32 板端运行 YOLO 作为当前原型架构。
- 不按固定每 2～3 秒拍照、实时视频上传或“必须同时使用 MQTT 与 WebSocket”作为首版验收条件。
- 不把道路检测、路线偏离、倒地判断、VLM 解释或真实红绿灯倒计时写成已实现功能。
- 旧文档中 `/api/location/upload` 等原型接口不再是正式设备协议；正式接口以 `/device/riderguard/telemetry` 与 `/device/riderguard/image` 为准。
