# 项目落地计划

> **现行基线：[RiderGuard 当前实施方案](RiderGuard_当前实施方案.md)。** STM32 只负责采集、上传和本地提醒；YOLO 在云端 Python 服务运行。下列阶段按现行协议调整。

## 第一阶段：框架落地与链路 MVP

- 引入 RuoYi-Vue-Plus 作为正式管理系统底座。
- 保留当前 FastAPI/Vue 最小代码用于原型验证，不再在其上重复实现通用后台能力。
- 在成熟框架中先完成设备、骑手、轨迹和风险事件业务模块。

- 设备端模拟器每秒生成定位、速度和设备状态，每约 4 秒上传 JPEG。
- 若依后端接收 `POST /device/riderguard/telemetry` 与 `POST /device/riderguard/image`，保存轨迹和私有照片。
- 前端首页展示设备数量、骑手数量、最近位置。
- 首版设备通过 HTTPS 上报，后台地图近实时轮询；MQTT/WebSocket 仅在规模与时延需要时再评估。

## 第二阶段：风险闭环

- 先完成普通/人群密集两档限速、板端超速提醒和后端事件处置；路线偏离、急刹、急转弯和倒地另列后续阶段。
- 建立 `user`、`device`、`track`、`risk_event` 数据模型。
- 风险事件保存图片地址、位置、速度、等级和分析结论。
- 管理后台增加风险列表、详情和轨迹回放。

## 第三阶段：真实感知和 AI

- 先接入 GNSS、霍尔车速、OV2640 摄像头、4G、本地蜂鸣器和状态灯；IMU 在后续行为检测阶段接入。
- 云端 Python 服务运行 YOLO，检测前方有效区域内的人数；用实拍数据校准区域、阈值和效果。
- 道路语义分割、GPS/视觉/IMU 风险融合与事后 VLM 解释单独采样和验收，不参与首版即时限速。

## 关键约定

- 正式设备接口使用 `capturedAtMs` 毫秒时间戳和每设备唯一 `sampleId`，支持去重与断网补传。
- `deviceId` 是设备端到云端的稳定主键，骑手绑定关系由后台维护。
- 端到端先保证“采集、上传、存储、展示、告警”闭环，再追求模型精度。
- 真实模型权重、采集数据、密钥和生产配置不提交到仓库。
