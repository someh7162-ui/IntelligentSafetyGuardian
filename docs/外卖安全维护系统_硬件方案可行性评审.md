# 外卖安全维护系统硬件方案可行性评审

## 评审结论

当前方案作为 **V1 采集型原型** 基本可行：STM32F407 负责 GNSS、IMU、霍尔测速和设备状态，4G 模块负责上行，服务器负责 YOLO 和大模型分析。

但是，当前 BOM 不能直接视为“全部已确定”。在你明确“不做实时视频传输、优先控制成本”后，摄像头风险可以降低，建议将状态调整为：

- **可直接保留**：STM32F407、ST-LINK、ATGM336H、MPU6050、3144 霍尔模块、2S 电池作为实验室原型组件。
- **采购前必须锁定规格**：4G 模块、OV2640 摄像头模块、DC-DC 模块。
- **必须补充的安全部件**：2S 电池保护/低压断电、输入反接保护、TVS、分路保险、蜂鸣器或指示灯、离线存储。
- **必须修改的软件策略**：图片从固定每 2~3 秒上传改为事件触发或低频采样，增加断网缓存和失败重传。

## 与原硬件设计文档的架构冲突

采购方案把 STM32 定义为“只采集与上传”，AI 全部放到服务器；原《安全守护盒硬件设计方案》则把 Raspberry Pi 5 定义为摄像头处理和轻量 AI 边缘主控。这两套方案不能同时作为同一代原型的主控架构。

建议当前项目明确采用采购方案的 **STM32 V1 采集型原型**，并把 Raspberry Pi 5 保留为后续边缘 AI 版本。否则摄像头接口、操作系统、供电功耗、通信协议和外壳空间都会重复设计。

## 关键风险

### 1. OV2640 无 FIFO：低频抓拍可以使用，但要限制单帧大小

OV2640 的 SCCB 配置和 DCMI 采集方向正确。无 FIFO 的 DVP 模块需要 STM32 直接接收一整帧数据，但你不传输实时视频，因此可以采用“拍一张、缓存、上传、再拍下一张”的串行流程。STM32F407VET6 通常只有 192 KB SRAM，JPEG 图片大小随场景变化，640×480 可能达到几十 KB 到上百 KB；还要给系统、DMA、4G 缓冲和协议栈留内存。

建议按以下优先级实现：

1. 第一版从 `320×240` 或 `640×480`、中低 JPEG 质量开始；
2. 先实测 100 张不同场景的最大 JPEG 大小，确认不会超过可用 SRAM；
3. 如果 640×480 超出内存，再降到 320×240 或增加 microSD/外部 SRAM；
4. 不需要为了低频抓拍强行更换成树莓派或高价摄像头。

另外，OV2640 的 JPEG 输出需要确认模块是否真的引出了 DCMI 所需的 `D0~D7、PCLK、VSYNC、HREF、XCLK`，不能只根据“支持 JPEG”判断可接通。

### 2. 4G 型号不能写成 Air780EP / M100M 二选一

这两个名称不代表同一个电气和 AT 指令规格。必须在下单前锁定一个确切 SKU，并确认：

- 模块芯片型号和 Cat.1/Cat.1 bis 制式；
- 供电输入到底是开发板 5V，还是裸模块约 3.4~4.3V；
- UART 电平是否为 3.3V TTL；
- 峰值电流和推荐电源容量；
- 是否支持 HTTP(S)、MQTT、文件分块和 TLS；
- SIM 卡座、频段、天线接口和天线是否包含。

若购买的是裸模块，不能直接接 5V。若购买的是 5V 开发板，5V 也必须接到开发板指定输入端。

### 3. 电源还缺少电池保护

2S LiPo 满电电压是 8.4V，不是 7.4V。B3 平衡充电器负责充电平衡，不等于设备运行时的过放、过流和短路保护。

建议电源链路改为：

```text
2S LiPo
  -> 2S 保护板/低压断电
  -> 总保险
  -> 反接保护 + TVS
  -> 总开关
  -> 主控 5V Buck / 4G 独立 Buck
```

两个 Buck 的输出必须在空载和带载时分别测量。4G 支路建议使用额定持续电流不低于 3A、峰值响应良好的模块，并在模块入口附近放置低 ESR 电解电容和 0.1µF 陶瓷电容。

### 4. 3A 总保险不一定合适

3A 保险丝对 1550mAh 航模电池和细杜邦线的保护能力有限。建议按照线材允许电流和系统实测峰值重新选型，并至少增加主路和 4G 支路的分路保护。杜邦线只适合桌面短线实验，不适合车辆长期振动环境。

### 5. 图片上传频率仍需控制

低频抓拍不等于低流量。如果仍然每 2~3 秒上传一次，会产生每分钟 20~30 张图片。即使单张 JPEG 只有 50~100KB，也会带来持续带宽、4G 功耗、服务器存储和接口重试压力。

建议改为：

- 正常状态：10~30 秒一张低分辨率缩略图，或只上传结构化状态；
- 触发超速、急刹、倒地、路线偏离等事件：立即上传 1 张主图和必要的前后缓冲图；
- 事件冷却时间：例如 10~30 秒，避免同一事件重复上传；
- 断网时先写入 SD/外部 Flash，恢复网络后按队列重传。

### 6. 本地报警部件缺失

原始硬件设计要求本地报警，但采购方案没有蜂鸣器、扬声器、LED 或驱动电路。建议增加：

- 3.3V 有源蜂鸣器或小型扬声器；
- N-MOSFET 或三极管驱动；
- 红/黄/绿状态 LED；
- 软件设置报警优先级和静音策略。

### 7. 接口复用必须用 CubeMX 实际核对

STM32F407 的 DCMI、I2C、UART、定时器输入捕获和 SWD 都涉及复用引脚。当前“接口类型”分配正确，但还没有具体引脚表。建议至少使用：

- 一个 UART 给 GNSS；
- 另一个 UART 给 4G；
- 独立 I2C 给 MPU6050；
- 定时器输入捕获给霍尔；
- DCMI + DMA 给摄像头；
- SWD 保留给 ST-LINK。

最终必须在 CubeMX 中检查 DCMI 与 I2C/UART/定时器的冲突，并画出正式原理图后再接线。

## 分模块判断

| 模块 | 判断 | 结论 |
|---|---|---|
| STM32F407VET6 | 可行 | 适合采集、规则判断和 AT 通信；不适合在本地做 YOLO |
| ST-LINK V2 | 可行 | SWDIO、SWCLK、GND，建议加 NRST |
| ATGM336H | 可行 | 需确认实际版本、3.3V 供电和有源天线供电方式 |
| MPU6050 GY-521 | 可行 | 必须用 3.3V 供电，避免模块上拉到 5V |
| 3144 霍尔模块 | 可行 | 3.3V 供电，DO 接定时器输入捕获；要做防抖和磁铁固定 |
| OV2640 无 FIFO | 有条件可行 | 低频单帧抓拍可以保留；先用低分辨率并实测最大 JPEG 大小 |
| Air780EP / M100M | 未锁定 | 必须确定一个 SKU 和完整电气规格 |
| 2S LiPo | 原型可行 | 必须增加运行时保护和低压断电 |
| B3 平衡充 | 可行 | 只用于充电，不替代电池保护板 |
| 双路 5V Buck | 可行 | 4G 支路需要足够峰值电流和滤波 |
| 杜邦线 | 仅实验室可行 | 车辆安装应改用锁扣端子、硅胶线和固定件 |

## 推荐的 V1.1 采购调整

### 保留

```text
STM32F407VET6
ST-LINK V2
ATGM336H + 陶瓷有源天线
MPU6050
3144 霍尔模块 + 磁铁
2S LiPo（仅原型）
B3 平衡充
```

### 改为“确认后采购”

```text
带 FIFO 的 OV2640 摄像头模块
确定型号的 Cat.1 开发板
额定 3A 以上且有峰值余量的 4G Buck
```

### 补充

```text
2S BMS/保护板或低压断电模块
TVS、防反接 MOSFET、分路保险
低 ESR 电解电容、0.1µF 陶瓷电容
蜂鸣器、LED、MOSFET 驱动
microSD 或外部 Flash
锁扣端子、硅胶线、热缩管、固定支架
```

## 推荐验证顺序

1. STM32 + ST-LINK + UART 日志；
2. STM32 + MPU6050；
3. STM32 + 霍尔测速；
4. STM32 + GNSS；
5. 单独验证 4G 开发板的供电、注册网络、HTTP(S)/MQTT 和峰值电流；
6. 单独验证 OV2640 的 DCMI 引脚、JPEG 帧大小和 DMA 缓冲；
7. 在实验室电源下完成整机上传闭环；
8. 加入电池保护、保险和外壳后再进行车辆道路测试。

## 最终判断

这套方案 **可以作为低成本 V1 原型继续推进**。在不做实时视频的前提下，当前 OV2640 可以保留，不必为了摄像头引入树莓派。摄像头和 4G 仍需在采购/接线前做规格确认。如果目标是稳定地实现“低频拍照、上传、云端识别”，最优先的改动是：

1. 从 320×240 或 640×480 低频单帧抓拍开始，并实测 JPEG 最大大小；
2. 锁定确切 4G SKU 并核对供电/电平；
3. 增加电池保护和本地报警；
4. 将正常图片上传频率控制在 10~30 秒或改为事件触发；
5. 用 CubeMX 固化 STM32 引脚分配。
